## 3. 何が審査されるか

DCON は「ものづくり（ハードウェア）× ディープラーニング × 事業プラン」の三点セットが必須で、
**現役VCが企業評価額で順位を付ける**。DCON2026 の最優秀は下水道点検ロボット「Pipe Eye」で 5億6000万円。
審査員5名の投資判断が全員 × になるチームもある。

### 一次審査（書類・アイデアベース可）── 11項目・0/1/3点

| 区分 | 項目 |
| :--- | :--- |
| 課題 | 課題の明確性 ／ 社会的意義 |
| 解決策 | 解決策の具体性 ／ 事業性 ／ 競合優位性 |
| DL | **DL活用の妥当性 ／ データ収集の具体性 ／ モデル実装計画** |
| HW | **ハードウェアの役割 ／ 設計 ／ 必然性 ／ 実装計画** |

提出物：エントリーシート（テキスト）＋補足資料（形式自由。システム構成図・ビジネスモデル図など）

### 二次審査（プロトタイプ）── 9項目・0/1/3/5点

課題解決の具体性 ／ 社会的意義 ／ **一貫した動作** ／ **DLの妥当性・実装の証明** ／
**HWの必然性・実装の証明** ／ 事業性 ／ 競合優位性

提出物：デモ動画（mp4）・説明資料（PDF）・**ソースコード**・概要サマリー・チーム特長・集合写真・意気込み・メンタリング希望

### 三次審査（面談）

プロダクト・事業の将来性 ／ チームの熱意・実現力 ／ 成長可能性・対話力

### 技術審査で見られること（本選レポートより）

「AIを使う」が OpenAI/Anthropic/Google の製品を呼ぶことではなく、
**学習データを用意し、訓練し、ハードに組み込む「開発」**を指すと明記されている。
そのうえで「LLM を会話に巧く使う」など複数技術の組み合わせが加点になる。
**API 呼び出しだけでは DL の要件を満たさない**と考えて計画する。

## 4. Overlai の現状と DCON 要件の差

| DCON の要件 | Overlai（`main`）の現状 | 差 |
| :--- | :--- | :--- |
| ハードウェア | スマホ PWA のみ | **無い** |
| 自作の学習モデル | `gpt-5.1` / Gemini を API で呼ぶだけ | **無い** |
| VC が評価する事業プラン | 基本無料＋サブスク、薬局導入（構想） | 弱い |
| 社会課題・競合優位性 | 「自宅在庫を判定基準にする」一点 | そのまま使える |
| 安全設計 | 知識ベース・裏取り・サーバー側上書き | そのまま強みになる |

## 5. 応用方針：「Overlai Shelf（仮）」

**家側に、勝手に在庫を覚える棚を足す。** 洗面台や救急箱の置き場に置くカメラ＋重量センサ付きの棚で、
出し入れした商品を自動で在庫登録・残量更新する。スマホの店頭スキャンはそのまま残し、棚が「家の状態」を供給する。

### ハードウェアの必然性（審査項目への答え）

- 判定の質＝在庫の正確さ。手入力の在庫は**登録されず、更新されず、消える**（`main` の #22 はまさにこれ）
- 市販薬・サプリ・化粧品は処方歴にもお薬手帳にも載らない。痕跡は**家の棚にしかない**
- 薬剤師が「本人の申告」ではなく「棚の事実」を見られるようになる

### 展示デモの筋書き

棚に置く → 自動登録 → 店頭スキャンで 🟡「家に残12錠」 → 棚から取り出す → 残量が減って判定が変わる。
「同じ商品でも在庫で判定が変わる」という企画の主張を、来場者の目の前で物理的に成立させる。

### 最小構成（プロトタイプ提出 2027年1月上旬に間に合う規模）

- Raspberry Pi 5 ＋ AI HAT（または Jetson Orin Nano）
- カメラモジュール（棚を俯瞰）
- ロードセル ＋ HX711（区画ごとの重量）
- 既存の Next.js アプリ（店頭スキャン・判定・ルーティン）はそのまま利用

## 6. ディープラーニングの計画（自作するもの／しないもの）

| # | タスク | 手法 | データ | 自作か |
| :---: | :--- | :--- | :--- | :---: |
| 1 | **商品の再識別** | 商品クラスが無限なので分類器ではなく**距離学習の埋め込み＋近傍検索**。初回はラベルを読んで登録、以後は外観で同定 | 自宅・ドラッグストアで多角度撮影＋拡張。まず100商品規模 | ✅ |
| 2 | 出し入れの検出と残量推定 | 重量差でイベント検出、画像で「どれが動いたか」を #1 に渡す。錠剤シートは重量差で残数 | 実測 | ルール |
| 3 | **成分表示の日本語OCR（オンデバイス）** | 成分表示に特化して文字認識モデルを追加学習。抽出を LLM Vision から外す | 成分表示の撮影画像＋正解テキスト | ✅ |
| 4 | 判定の文言生成 | 既存の LLM ＋ `lib/knowledge.ts` ＋ `lib/verify.ts` | — | LLM |

**「なぜ抽出は自作で、判定は LLM なのか」**を答えられるようにする。
判定側の安全設計（[DEVELOPMENT.md §5](DEVELOPMENT.md)）は DCON でもそのまま守る。

#3 は `main` の課題 #24（レイテンシ）・コスト・オフライン動作にも同時に効く。

## 7. 事業プラン：払い手を薬局に置き換える

家庭向けハードの売り切りは利幅が薄く、VC は評価しない。

- **払い手：かかりつけ薬局・在宅医療の薬局。** 薬剤師は患者が家で使う市販薬・サプリ・化粧品を把握できない。
  高齢者のポリファーマシー対策で厚労省指針が求める「一般用医薬品・サプリの併用把握」の穴がここ
- 薬局が患者宅に棚を貸与し、患者ごとの月額を払う。患者側のアプリは無料で店頭判定を使えて、獲得チャネルになる
- 既存の服薬支援ロボは**処方薬しか扱わない**。「処方外のものを見る」が差別化の一点
- 企画書の「小売への送客は利益相反なので採らない」はこの組み替えと矛盾しない

### 先に整理しておく法的な論点

薬局と在庫を共有するにはサーバーが要り、`main` の「端末内に留める」設計から変わる。
要配慮個人情報の同意設計と医療機器該当性を、エントリーシートで「認識して設計に組み込む」と明記し、VC の突っ込みを先回りする。

## 8. 検討して見送った案

| 案 | 見送った理由 |
| :--- | :--- |
| 調剤薬局の OTC カウンターに置く店頭スキャナー | 「自宅在庫」という独自性が消える |
| 洗面台ミラー型の塗る順序ナビ | 展示映えはするが事業性が弱い |
