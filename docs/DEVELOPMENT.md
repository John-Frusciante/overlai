# 開発ガイド

このリポジトリで作業を始める人が最初に読むファイル。

---

## 1. 動かす

```bash
npm install
npm run dev          # http://localhost:3000
```

APIキーは**なくても動く**。未設定ならモックモードで起動する（§3）。

| コマンド | 用途 |
| :--- | :--- |
| `npm run dev` | 開発サーバー |
| `npx tsc --noEmit` | 型チェック。**コミット前に必ず通す** |
| `npx next build` | 本番ビルド |
| `vercel --prod --yes` | 本番デプロイ |

## 2. まず見るべき画面

| URL | 何が分かるか |
| :--- | :--- |
| `/preview` | 判定カードの3色。このアプリの中核 |
| `/?demo=red` | マイストック → スキャン → 🔴判定 の一連の流れ |
| `/routine` | 洗う順序・塗る順序の自動ソート |

## 3. モックモードと本番モード

```
ANTHROPIC_API_KEY 未設定  →  モックモード（lib/mock.ts の固定応答）
ANTHROPIC_API_KEY 設定済  →  本物のAIパイプライン
OVERLAI_MOCK=1           →  キーがあっても強制的にモック
```

**切り替えにコード変更は不要。** 環境変数だけで決まる（`app/api/*/route.ts` の `useMock()`）。

モック時の判定シナリオは `?demo=yellow|red|blue` で選ぶ。マイストックからスキャン画面へ引き継がれるため、撮影の流れを止めずにシナリオを固定できる。

本物に切り替えるとき：

```bash
echo 'ANTHROPIC_API_KEY=sk-ant-...' > .env.local
```

## 4. どこに何を書くか

| 書きたいもの | 置く場所 |
| :--- | :--- |
| 新しいデータ構造 | `lib/types.ts` |
| AIへの指示 | `lib/prompts.ts`（**他の場所に散らさない**） |
| AI出力のスキーマ | `lib/schemas.ts` |
| localStorage の読み書き | `lib/storage.ts`（**コンポーネントから直接呼ばない**） |
| ルールベースの判定ロジック | `lib/routine.ts` `lib/expiry.ts` |
| リクエストの検証 | `lib/request.ts`（両APIで共有） |
| 画面 | `app/*/page.tsx` |
| 再利用するUI | `components/` |

### 集約している理由

| ファイル | 理由 |
| :--- | :--- |
| `lib/prompts.ts` | プロンプトはデモ直前に最も差し替えたくなる。散らばると変更漏れが起きる |
| `lib/storage.ts` | 将来ネイティブ化する際、差し替えるのはこのファイルだけで済むようにする |
| `lib/types.ts` | 型定義がUI・API・プロンプトの共通言語になる |

## 5. 壊してはいけない制約

**これらは思いつきで決めたものではなく、失敗や検討を経て決まったもの。** 変更する前に理由を読むこと。

### 5.1 シードの内服薬に処方NSAIDsを置かない

`lib/seed.ts` に処方のロキソプロフェン等を追加してはならない。

処方NSAIDsが在庫にあると、市販イブプロフェン製剤のスキャンが「NSAIDsの重複投与＝過量摂取リスク」として🔴の条件にも該当し、**デモの主役である🟡判定が不安定になる**。

判定ルールは医学的に正しい。**ルールではなくシードを調整する。**

### 5.2 安全に関わる値をLLMに委ねない

```ts
// app/api/analyze/route.ts
consult_recommended: raw.signal === 'red' ? true : raw.consult_recommended,
reasons: raw.reasons.filter((r) => r.ingredient.trim().length > 0),
```

赤判定なら相談導線を必ず出す。成分名のない理由は根拠として成立しないので落とす。**プロンプトのお願いに頼らない。**

### 5.3 判定の effort を下げない

`/api/analyze` のステップ2は `effort: 'high'`。判定品質がそのまま評価対象になる。レイテンシを削るなら**ステップ1だけ**を `medium` → `low` の順に下げる。

### 5.4 thinking を無効化しない

`claude-opus-5` は adaptive thinking が既定でオン。無効化するとツール呼び出しや内部タグが本文に混入する既知の失敗モードがある。レイテンシは `effort` で調整する。

`max_tokens` は 16,000。**thinking トークンもここから消費される**ため、切り詰めると出力が途中で切れる。

### 5.5 `localStorage` をコンポーネントから直接呼ばない

`lib/storage.ts` を経由する。この1点を守るかどうかで、将来のネイティブ化が「1ファイルの差し替え」か「全面調査」かに分かれる。

### 5.6 APIキーをクライアントに出さない

`ANTHROPIC_API_KEY` は Route Handler でのみ読む。`NEXT_PUBLIC_` を付けない。

### 5.7 断定表現を使わない

医療に隣接するため、判定文言は「〜の可能性があります」で統一する。診断・治療方針・用法用量の指示を行わない。相談導線は**全判定色で**常設する（🔴だけではない）。

## 6. 変更を加えるときの手順

1. `docs/STATUS.md` で現状を確認する
2. 変更する（§5 の制約に触れていないか確認）
3. `npx tsc --noEmit` を通す
4. 影響する画面を実際に開いて確認する
5. `docs/STATUS.md` と `docs/ARCHITECTURE.md` を更新する
6. コミットする

### コミットメッセージ

日本語で書く。1行目に要約、空行、本文に「何を」「なぜ」を書く。

```
ルーティン・在庫登録・期限管理・服薬記録を実装

企画書の機能一覧のうち未実装だった部分を追加した。

- 今日のルーティン画面（3画面目）
  洗う順序・塗る順序を剤形と基剤からルールベースでソート。
```

## 7. よくある落とし穴

| 症状 | 原因 |
| :--- | :--- |
| AIが動かない | `.env.local` に `ANTHROPIC_API_KEY` が無い。モックが返っている（サーバーログに警告が出る） |
| カメラが起動しない | HTTPSでないと `getUserMedia` は動かない。`localhost` は例外的に可 |
| 判定が毎回同じ | モックモード。`?demo=` を変えるかキーを設定する |
| 出力が途中で切れる | `max_tokens` を絞りすぎ。thinking トークンの分を見込む |
| 在庫が増えない | `lib/seed.ts` はシードであり、実データは localStorage にある。`/` の「編集 → 初期化」で戻せる |
| 型エラー `form が無い` | `StockItem` に `form`（剤形）は必須。順序ソートのキーになる |
