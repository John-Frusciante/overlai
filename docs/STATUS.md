## AIは実際に動いている

学校配布の Azure OpenAI 互換プロキシ（`gpt-5.1`）で、2段階パイプラインが本番稼働している。

| ステップ | モデル | 実測 |
| :--- | :--- | :---: |
| 1. 成分抽出（Vision） | `gpt-5.1` | 4.7秒 |
| 2. 在庫照合判定 | `gpt-5.1` | 4.1秒 |
| **合計（ローカル）** | | **8.6〜9.3秒** |
| 合計（本番・コールドスタート込み） | | 10.6秒 |
| ルーティンの解説（`/api/routine`） | `gpt-5.1` | 6.5秒 |

NFR-01（10秒以内）をローカルでは満たしている。

AIを呼ぶ経路は3つある — 成分抽出（Vision）、在庫照合判定、ルーティンの解説。どれも同じプロバイダのチェーンに乗る。

プロバイダは `lib/llm.ts` が環境変数から決める。**Anthropic Claude / Azure OpenAI / Google Gemini / モックの4経路**があり、コード変更なしで切り替わる。

```
OVERLAI_MOCK=1     → モック（AIを呼ばない。デモの保険）
ANTHROPIC_API_KEY  → Anthropic Claude (claude-opus-5)
AZURE_PROXY_KEY    → Azure OpenAI プロキシ (gpt-5.1)  ← 本番はこれが先頭
GEMINI_API_KEY     → Google Gemini (gemini-3.5-flash / gemini-3.6-flash)
いずれも無し        → モック
```

キーがあるものを上から順に使い、**失敗したら次に落ちる**。本番は学校配布のプロキシ1本に依存していて、クォータ超過やキー失効が起きた瞬間にAI機能が全部止まる。Gemini はそのための保険で、狙いは品質ではなく独立した事業者のクォータに乗ること（[ARCHITECTURE.md §7](ARCHITECTURE.md)）。

### 補足が必要なもの

**#4 服用カレンダー** — 飲むタイミング（朝・昼・夜）・1回量・残量を `/stock/new` から設定できる。設定した薬だけが「今日のお薬」に並び、チェックすると残薬が減る。

**#11 順序ソート** — 並び順は剤形の重みで決めるルールベース（`lib/routine.ts`）。**その上に、在庫の顔ぶれと肌質・頭皮に応じた一言をAIが足す**（`POST /api/routine`）。順序と言葉を切り離しているので、AIが落ちても並び順と理由は出続ける（[ARCHITECTURE.md §4.6](ARCHITECTURE.md)）。**順番はユーザーが手で入れ替えられる**（剤形どおりに戻す導線つき）。

**#13 洗浄基剤 × 肌質** — 実装済み。成分名から洗浄基剤の系統（アミノ酸系／ベタイン系／高級アルコール系／石鹸系）を判定し、肌質・頭皮の自己申告と突き合わせる。**AIを使わずルールベースなので、モックモードでも本物として動く。** 肌質・頭皮の全5値／全4値に対して判定が出る（以前は頭皮×石鹸系と「普通」「混合」が抜けていた）。

### 在庫を変えると判定が変わることの実証

御岳百草丸を**在庫に追加してから同じ商品を再スキャン**したところ、判定が 🔵 → 🟡 に変わった。

| 状態 | 判定 |
| :--- | :---: |
| 百草丸が在庫に無い | 🔵 買っても問題なさそう |
| 百草丸を在庫に追加後 | 🟡 家にあります |

**商品は同じで、変わったのは在庫だけ。** 判定の基準が商品ではなくその人の家にあることを、
同一商品で直接示せる。商品データベースで戦う既存サービスには原理的にできない実演であり、
企画書 §2 の主張（「商品DBをどれだけ大きくしても『もう持っている』だけは言えない」）に直接対応する。

あわせて、在庫の追加（`/stock/new`）→ localStorage 保存 → 判定への反映という経路が
実機で動作することも確認できた。

**光沢・曲面・小さい文字の実物でも読み取りが成立することを確認した。**
成分名に軽微な誤読（「ペラドンナ」「ジフェニルピリン」）が生じても、薬効分類での照合により判定は正しく行われる。

この検証で2種類のバグを発見・修正した。生成画像のテストでは見つからなかったもの。

| 種類 | 内容 |
| :--- | :--- |
| 見落とし（false negative） | かぜ薬の抗ヒスタミン重複を🔵と判定していた → 薬効分類での照合を追加 |
| 過剰警告（false positive） | 防腐剤（フェノキシエタノール等）で🔴を出していた → 刺激リスクの範囲を限定列挙 |

**判定の信頼性は「警告すべきを警告する」と「無駄な警告を出さない」の両方で決まる。**
| Vision と Structured Outputs（strict）がプロキシで通る | 直接叩いて確認 |
| 型チェック・本番ビルドが通る | `npx tsc --noEmit` / `npx next build` |
