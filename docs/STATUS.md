## AIは実際に動いている

学校配布の Azure OpenAI 互換プロキシ（`gpt-5.1`）で、2段階パイプラインが本番稼働している。

| ステップ | モデル | 実測 |
| :--- | :--- | :---: |
| 1. 成分抽出（Vision） | `gpt-5.1` | 4.7秒 |
| 2. 在庫照合判定 | `gpt-5.1` | 4.1秒 |
| **合計（ローカル）** | | **8.6〜9.3秒** |
| 合計（本番・コールドスタート込み） | | 10.6秒 |

NFR-01（10秒以内）をローカルでは満たしている。

プロバイダは `lib/llm.ts` が環境変数から決める。**Anthropic Claude / Azure OpenAI / モックの3経路**があり、コード変更なしで切り替わる。

```
OVERLAI_MOCK=1     → モック（AIを呼ばない。デモの保険）
ANTHROPIC_API_KEY  → Anthropic Claude (claude-opus-5)
AZURE_PROXY_KEY    → Azure OpenAI プロキシ (gpt-5.1)  ← 現在これ
いずれも無し        → モック
```

### 在庫を変えると判定が変わることの実証

御岳百草丸を**在庫に追加してから同じ商品を再スキャン**したところ、判定が 🔵 → 🟡 に変わった。

| 状態 | 判定 |
| :--- | :---: |
| 百草丸が在庫に無い | 🔵 買っても問題なさそう |
| 百草丸を在庫に追加後 | 🟡 家にあります |

**商品は同じで、変わったのは在庫だけ。** 判定の基準が商品ではなくその人の家にあることを、
同一商品で直接示せる。商品データベースで戦う既存サービスには原理的にできない実演であり、
企画書 §2 の主張（「商品DBをどれだけ大きくしても『もう持っている』だけは言えない」）に直接対応する。

あわせて、在庫の追加（`/stock/new`）→ localStorage 保存 → 判定への反映という経路が
実機で動作することも確認できた。

**光沢・曲面・小さい文字の実物でも読み取りが成立することを確認した。**
成分名に軽微な誤読（「ペラドンナ」「ジフェニルピリン」）が生じても、薬効分類での照合により判定は正しく行われる。

この検証で2種類のバグを発見・修正した。生成画像のテストでは見つからなかったもの。

| 種類 | 内容 |
| :--- | :--- |
| 見落とし（false negative） | かぜ薬の抗ヒスタミン重複を🔵と判定していた → 薬効分類での照合を追加 |
| 過剰警告（false positive） | 防腐剤（フェノキシエタノール等）で🔴を出していた → 刺激リスクの範囲を限定列挙 |

**判定の信頼性は「警告すべきを警告する」と「無駄な警告を出さない」の両方で決まる。**
| Vision と Structured Outputs（strict）がプロキシで通る | 直接叩いて確認 |
| 型チェック・本番ビルドが通る | `npx tsc --noEmit` / `npx next build` |

## 品質テスト（2026年9月9日）

### 判定の一貫性

同じ画像を3回ずつスキャンし、判定が揺らがないことを確認した。**デモ中に色が変わると致命的**なため。

| シナリオ | 3回の結果 | 所要 |
| :--- | :--- | :--- |
| 🟡 鎮痛薬 | YELLOW / YELLOW / YELLOW | 9.8〜11.5秒 |
| 🔴 薬用化粧水 | RED / RED / RED | 9.4〜10.1秒 |
| 🔵 シャンプー | BLUE / BLUE / BLUE | 7.8〜9.0秒 |

**9回すべて期待どおり。揺らぎなし。**

### エラー系の実挙動

| 入力 | 応答 |
| :--- | :--- |
| 成分表示が写っていない画像 | 422 `EXTRACTION_FAILED`「成分表示に寄せて撮り直してください」 |
| 不正な画像形式 | 400 `INVALID_IMAGE` |
| 画像なし | 400 `INVALID_IMAGE` |
| 在庫が空 | 400 `EMPTY_STOCK`「先にストックを追加してください」＋追加画面への導線 |

在庫が空のケースは当初 `INVALID_IMAGE`「在庫データが不正です」を返しており、
ユーザーが次に何をすべきか分からない状態だったため、専用コードと導線を追加した。
