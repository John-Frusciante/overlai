## 6. ここから導かれる開発方針

### 提出物から逆算する

デモ動画とピッチ動画（1分）が提出物である以上、**映像に映らない機能は評価されない**。

- ✅ 優先：判定結果の画面、スキャンの流れ、AIが動いている感触
- ❌ 後回し：認証、DB、登録フロー、通知、設定画面

### 評価軸に直接効く実装を選ぶ

| 評価軸 | 実装で示す方法 |
| :--- | :--- |
| 技術力 | 2段階のAIパイプライン（成分抽出 → 在庫照合判定）。単一プロンプトにしなかった理由を説明できること |
| 実装力 | 実機（スマホ・https）で実際に動くこと。Vercelにデプロイして公開URLを用意する |
| 実用性 | 実在の商品を撮って判定が出ること。ダミーデータだけのデモにしない |
| 社会的インパクト | 過剰摂取の防止、外用薬アドヒアランス、無駄買い削減 |

### 「なぜ作ったか」を必ず用意する

主催側が評価の核心と明記している。**作品概要書とピッチに、応募者自身の具体的な体験を必ず入れる。**
現在の企画書では以下2箇所が空欄のまま：

- 企画書 1章：課題の体験談（3〜4行）
- 企画書 11章：なぜ私がこれを作るのか（5〜6行）

### 安全性の説明を用意しておく

医療・医薬品に隣接するため、審査員から必ず問われる想定。

- 診断・治療判断は行わない
- 断定表現を使わず「〜の可能性があります」で統一
- 判定理由に必ず成分名を含める（根拠なき警告を出さない）
- 薬剤師・皮膚科への相談導線を常設
- プログラムの医療機器該当性については、記録・情報提示の範囲に留める設計

**これらはプロンプトレベルで制約として実装済み**（`app/api/analyze/route.ts` 参照）。実装で守っていることを概要書に書く。
