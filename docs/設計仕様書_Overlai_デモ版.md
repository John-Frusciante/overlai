## 0. このドキュメントの位置づけ

企画書は「何を作るか・なぜ作るか」を扱う。本書は**その一部をコンテスト提出物として実装するための、実装着手可能な粒度の要求・要件・設計**を定義する。

本書で確定させるのは以下4点。

1. **何を作らないか**（スコープ境界の明文化。締切まで残り時間が限られるため、これが最重要）
2. **AIパイプラインの入出力契約**（プロンプト・スキーマ・判定ルール）
3. **API仕様とデータモデル**（実装者が迷わない粒度）
4. **受け入れ基準**（「完成」の定義）

### 用語

| 用語 | 定義 |
| :--- | :--- |
| **ストック** | ユーザーの自宅にある薬・コスメ・バス用品。判定の基準となるデータ |
| **スキャン** | 店頭商品のパッケージ／成分表示を撮影し、AIに解釈させる操作 |
| **判定（Judgement）** | スキャン結果とストック全件を突合して得られる3色シグナル＋根拠 |
| **ステップ1 / 抽出** | 画像 → 成分構造化JSON（Vision） |
| **ステップ2 / 照合** | 抽出結果＋ストック → 判定JSON |

## 1. 要求定義（なぜ作るか）

### 1.1 このデモが達成すべきこと

コンテスト開発部門の評価軸は **技術力・実装力・実用性・社会的インパクト** であり、主催側は「なぜ作ったか」を評価の核心と明記している。提出物は**作品概要書・デモ動画・ピッチ動画（1分）**の3点。

したがってこのデモの目的は「製品として完成させること」ではない。

> **目的：「自宅在庫を判定基準にする」という発想が、実際に動くソフトウェアとして成立することを、映像で証明する。**

### 1.2 デモで証明したい仮説（優先順）

| # | 仮説 | 証明手段 | 対応する評価軸 |
| :--- | :--- | :--- | :--- |
| H-1 | 自宅在庫を基準にすると、商品DBでは出せない判定が出せる | 🟡判定：同成分が家にある → 「買わなくて大丈夫」 | 実用性・社会的インパクト |
| H-2 | 外用薬 × 化粧品という空白領域を、生成AIなら扱える | 🔴判定：ステロイド外用中の肌 × アルコール系化粧水 | 技術力・社会的インパクト |
| H-3 | 非定型な成分表示を、公式DBなしで構造化できる | 実在商品のパッケージを撮影して成分抽出が通る | 技術力・実装力 |
| H-4 | 医療隣接領域として安全に設計されている | 根拠成分の常時併記・断定回避・相談導線 | 実用性（審査員の必問対策） |

**H-1 と H-2 の両方を映せないと企画の半分しか伝わらない。** デモ動画は🟡と🔴の2本を必ず流す。

### 1.3 非ゴール（このデモでは達成しない）

- 医療機器・医薬品としての正確性の担保（§12 の免責範囲で運用）
- 実運用に耐えるデータ永続化、マルチユーザー、認証
- 網羅的な成分知識ベースの構築
- 商品バーコード（JAN）からの商品特定 ← **日本に公式DBが存在しないため設計上放棄する**（§7.1）

### 1.4 ステークホルダー

| 立場 | 関心事 | 本書での対応箇所 |
| :--- | :--- | :--- |
| 審査員（企業実務者） | 技術的妥当性、社会的意義、薬機法リスク | §7・§12 |
| 応募者（開発者） | 締切内に確実に動くこと | §13・§14 |
| デモ視聴者 | 何が起きているか3秒で分かること | §9 |

## 2. スコープ定義

### 2.1 実装する（In Scope）

| ID | 項目 | 理由 |
| :--- | :--- | :--- |
| S-1 | マイストック画面（シードデータ表示） | 判定の前提が「家にあるもの」だと視覚的に示すため |
| S-2 | スキャン画面（カメラ ＋ 画像アップロード） | デモの操作の中心 |
| S-3 | 成分抽出API（画像 → 構造化JSON） | H-3 の証明 |
| S-4 | 判定API（抽出結果＋ストック → 3色判定） | H-1・H-2 の証明 |
| S-5 | 判定カード画面（3色・根拠展開・相談導線） | デモの山場。H-4 の証明 |
| S-6 | Vercelデプロイ（HTTPS公開URL） | 実機カメラは HTTPS 必須。実装力の証明 |

### 2.2 実装しない（Out of Scope）— 明示的に捨てる

| 項目 | 捨てる理由 | デモでの代替 |
| :--- | :--- | :--- |
| ユーザー登録・ログイン | 映像に映らない | 単一ユーザー前提 |
| データベース（RDB/KV） | 映像に映らない | シードJSON ＋ localStorage |
| 医療用QRコード（JAHIS）読み取り | 仕様調査コストが締切に見合わない | ストックに登録済みの状態から始める |
| レシート一括登録 | 同上 | 同上 |
| 服用カレンダー・残薬カウント・通知 | 映像に映らない | なし |
| JANコード → 商品DB照合 | **日本に公式DBが存在しない**（§7.1） | 成分表示の直接撮影 |
| 塗る／洗う順序ナビ | 実装コスト大 | 静止画モック1枚（余力があれば） |
| ストックの追加・編集UI | 判定の証明に不要 | シードデータ固定 |

**判断基準：迷ったら「デモ動画のどのカットに映るか」を問う。映らないなら作らない。**

## 3. ユースケース

### UC-1：買わなくていいと分かる（🟡・主シナリオ）

```
前提：ストックに「イブA錠（イブプロフェン）残12錠」が登録済み
      かつ、処方薬にNSAIDsが含まれないこと（§6.2 の設計上の注意）

1. ユーザーがマイストック画面を開く         → 家にあるものが7件並ぶ
2. FAB「スキャン」をタップ                  → カメラ起動
3. 店頭のイブプロフェン製剤にかざす          → 撮影
4. 抽出中（1〜3秒）                        → ローディング表示
5. 判定カード：🟡「買わなくて大丈夫です」    → 検出成分「イブプロフェン 150mg」
6. 「根拠を見る」をタップ                   → 家の該当品と理由が展開
```

### UC-2：使っている薬との相性に気づく（🔴・主シナリオ）

```
前提：ストックに「ステロイド外用薬（ベタメタゾン吉草酸エステル）使用中・顔」が登録済み

1〜4 は UC-1 と同じ（対象は化粧水のパッケージ）
5. 判定カード：🔴「注意が必要です」          → 検出成分「エタノール／サリチル酸」
6. 「根拠を見る」                           → 該当処方薬と、刺激の可能性の説明
7. 「薬剤師・皮膚科に相談」ボタンが常設されている
```

### UC-3：買っていい（🔵・補助シナリオ）

判定エンジンが「なんでも警告を出す装置」ではないことを示すために必要。デモ動画に入れるかは尺次第だが、**実装はする**（審査員の質疑で「全部黄色になるんじゃないの？」と必ず聞かれる）。

| ID | 機能 | 優先度 | 受け入れ条件 |
| :--- | :--- | :--- | :--- |
| FR-01 | ストック一覧をカテゴリ別に表示する | **必須** | 4カテゴリ・7件が表示され、各件に商品名・主要成分タグ・状態が出る |

| FR-06 | 抽出結果とストック全件から3色判定を返す | **必須** | §7.4 の判定ルールに従い signal が決まる |

## 6. データモデル

### 6.1 StockItem（自宅在庫）

```ts
type StockCategory = '処方薬' | '処方薬(外用)' | '市販薬・サプリ' | 'スキンケア' | 'ヘアケア';

interface StockItem {
  id: string;              // 'stk-001'
  name: string;            // 'イブA錠'
  category: StockCategory;
  ingredients: string[];   // ['イブプロフェン', 'アリルイソプロピルアセチル尿素']
  status: string;          // '残12錠' / '使用中・顔' / '開封2ヶ月'
  isPrescription: boolean; // 処方薬フラグ（判定で赤の条件に使う）
  bodyPart?: string;       // '顔' — 外用薬の適用部位
}
```

### 6.2 シードデータ（デモ固定・7件）

この7件で🔵🟡🔴すべてを出せることを確認済みの構成。

| id | 商品名 | category | 主要成分 | status | isPrescription |
| :--- | :--- | :--- | :--- | :--- | :---: |
| stk-001 | フェキソフェナジン塩酸塩錠60mg（処方） | 処方薬 | フェキソフェナジン塩酸塩 | 残14日分 | ✓ |
| stk-002 | イブA錠 | 市販薬・サプリ | イブプロフェン, アリルイソプロピルアセチル尿素 | 残12錠 | |
| stk-003 | ヒルドイドローション（処方） | 処方薬(外用) | ヘパリン類似物質 | 使用中・顔 | ✓ |
| stk-004 | ベタメタゾン吉草酸エステル軟膏（処方） | 処方薬(外用) | ベタメタゾン吉草酸エステル | 使用中・顔 | ✓ |
| stk-005 | ◯◯美容液 | スキンケア | ナイアシンアミド | 開封2ヶ月 | |
| stk-006 | △△化粧水 | スキンケア | グリセリン, BG | 開封1ヶ月 | |
| stk-007 | □□シャンプー | ヘアケア | ココイルグルタミン酸TEA | 使用中 | |

**判定の出方（設計意図）**

- 市販のイブプロフェン製剤をスキャン → stk-002 と**同一成分**が重複 → 🟡
- アルコール系・サリチル酸配合の化粧水をスキャン → stk-004（ステロイド外用・顔）と競合 → 🔴
- ワックス落とし用シャンプーをスキャン → stk-007 と用途が異なる → 🔵

> **⚠ 設計上の注意：内服薬のシードに処方NSAIDsを置いてはならない。**
> 処方のロキソプロフェン等が在庫にあると、市販イブプロフェン製剤のスキャンは「NSAIDsの重複投与＝過量摂取リスク」として**🔴側の条件にも該当**し、デモの主役である🟡判定が不安定になる（§7.4 決定表の優先1）。
> **判定ルールは医学的に正しく、シードの組み方が誤っていた。** ルールを緩めるのではなくシードを差し替えることで、安全設計を弱めずに🟡を安定して出す。stk-001 を抗アレルギー薬にしてあるのはこのためである。

### 6.3 ExtractionResult（ステップ1の出力）

```ts
interface ExtractionResult {
  product_name: string | null;
  category: '市販薬' | 'スキンケア' | 'ヘアケア' | 'サプリ' | '不明';
  form: '錠剤' | 'カプセル' | '化粧水' | '乳液' | 'クリーム' | '軟膏' | 'シャンプー' | '不明';
  ingredients: string[];        // 記載順（配合量の多い順）を保持
  confidence: 'high' | 'medium' | 'low';
}
```

> **`ExtractionResult.category` と `StockCategory`（§6.1）は別軸であり、値が一致しないのは意図的。** 前者は店頭商品の分類（処方薬は店頭に並ばないため選択肢に持たない）、後者は自宅在庫の分類（処方の内服・外用を区別する必要がある）。実装時に一方をもう一方へキャストしないこと。

### 6.4 Judgement（ステップ2の出力）

```ts
type Signal = 'blue' | 'yellow' | 'red';
type ReasonType = '成分重複' | '効能重複' | '刺激リスク' | '吸収阻害';

interface Reason {
  type: ReasonType;
  ingredient: string;      // 該当成分名（必須・空文字禁止）
  detail: string;          // なぜそう判定したか
  related_item: string;    // 自宅アイテム名
}

interface Judgement {
  signal: Signal;
  headline: string;           // 20字以内
  summary: string;            // 1〜2文
  matched_item_ids: string[]; // StockItem.id の配列
  reasons: Reason[];
  consult_recommended: boolean;
}
```

## 7. AI処理仕様

### 7.1 設計判断：なぜJANコードを使わないのか

化粧品の JAN → 全成分の公式データベースは**日本に存在しない**。医薬品は添付文書がPMDAにあるが、化粧品の全成分は各社の任意開示に留まる。

したがって本デモは**バーコードではなくパッケージの成分表示そのものを読む**設計を採る。これは妥協ではなく、非定型な表示を解釈できる生成AIでなければ実装できない方式であり、**そのまま「なぜ生成AIが必要か」の説明になる**。概要書・ピッチともにこの論理で説明する。

### 7.2 設計判断：なぜ2段階に分けるのか

単一プロンプトで「画像を見て判定まで出せ」とすると、次の3点が崩れる。

1. **精度** — 読み取りと推論を同時に要求すると、成分の取りこぼしが増える
2. **検証可能性** — ユーザーが「何を読み取ったか」を確認できない＝ハルシネーション対策が成立しない
3. **デバッグ性** — 判定がおかしいとき、読み取りの問題か推論の問題か切り分けられない

**この分割理由は概要書の技術ポイントとしてそのまま使える。**

```
[画像] ──ステップ1（Vision＋構造化出力）──> [ExtractionResult]
                                                    │
                                    [StockItem[]] ──┤
                                                    ↓
                                        ステップ2（構造化出力）
                                                    ↓
                                              [Judgement]
```

### 7.3 ステップ1：成分抽出

| 項目 | 内容 |
| :--- | :--- |
| 入力 | 画像（base64、JPEG、長辺1568px以下） |
| 出力 | `ExtractionResult`（§6.3） |
| 出力保証 | **構造化出力（`output_config.format`）でスキーマを強制**。JSONパース失敗は原理的に起こらない |
| effort | `medium`（読み取り主体だが、精度が判定品質の上流。§7.5 のチューニング方針に従う） |
| thinking | 既定（adaptive）のまま。**明示的に無効化しない**（§7.5） |

**プロンプト要点**

- 商品パッケージの成分表示を読み取り、スキーマに従って構造化する
- **読み取れない文字は推測せず省略する**（ハルシネーション抑止）
- 全成分表示は**記載順（配合量の多い順）を保持**する
- 商品名が判読できない場合は `product_name: null`、憶測で商品を特定しない
- 画像が不鮮明・成分表示が写っていない場合は `confidence: "low"` を返す

> **注記**：旧要件定義書にあった「JSONのみを返す。Markdownコードフェンス禁止」というプロンプト指示は**不要**。構造化出力を使えばスキーマ準拠が保証されるため、プロンプトで整形を懇願する必要はない。

### 7.4 ステップ2：在庫照合判定

| 項目 | 内容 |
| :--- | :--- |
| 入力 | `ExtractionResult` ＋ `StockItem[]`（全件） |
| 出力 | `Judgement`（§6.4） |
| 出力保証 | 構造化出力でスキーマ強制 |
| effort | `high`（既定値。成分間の関係推論が判定品質そのもの。**ここは下げない**） |
| thinking | 既定（adaptive）のまま |

**判定ルール（決定表・上から評価し、最初に該当した色を採用）**

| 優先 | signal | 条件 | 例 |
| :---: | :---: | :--- | :--- |
| 1 | 🔴 red | ストック内の**処方薬（内服・外用）**との併用で、リスク・強い刺激・**過量摂取**・**吸収阻害**が想定される成分を含む | ステロイド外用中の顔にエタノール／サリチル酸配合の化粧水／処方NSAIDs服用中に市販の同系鎮痛薬 |
| 2 | 🟡 yellow | ストックに**同一成分**または**同効能**の**市販品**が存在し、**用途も同じ**（処方薬が絡まない） | 手持ちのイブA錠と同じイブプロフェン／手持ち美容液とナイアシンアミドが重複 |
| 3 | 🔵 blue | 上記いずれにも該当しない。**成分が一部重なっていても用途が明確に異なれば blue** | 普段使いのシャンプーと、ワックス落とし用 |

> **🟡と🔴の境界は「処方薬が絡むか」。** 同じ「成分が重複している」でも、処方薬との重複は**過量摂取リスク**なので🔴、市販品同士の重複は「買う必要がない」なので🟡。この線引きが安全設計の中核であり、デモの都合で緩めてはならない（§6.2 でシード側を調整したのはこのため）。

**安全制約（プロンプトに明記・§12 と対応）**

| 制約 | 実装方法 |
| :--- | :--- |
| 断定表現を使わない | 「〜の可能性があります」で統一するようプロンプトで指示 |
| 診断・治療方針を提示しない | 疾患名の推定・用法用量の指示を禁止 |
| 根拠なき警告を出さない | `Reason.ingredient` を必須フィールドにし、**スキーマレベルで**成分名の併記を強制 |
| 赤なら必ず相談を促す | `signal === 'red'` のとき `consult_recommended: true` を返すようプロンプトで指示し、**サーバー側でも上書き強制**する |

> **`consult_recommended` はモデル出力を信用せず、サーバー側で `signal === 'red' ? true : result.consult_recommended` と上書きする。** 安全に関わる値をLLMの気分に委ねない、という設計そのものが審査員への説明材料になる。

### 7.5 プロバイダとモデル選定

**プロンプトとスキーマはプロバイダに依存しない設計**にした（`lib/llm.ts`）。差し替わるのは呼び出し方だけで、2段階パイプラインの構造は変わらない。

```
OVERLAI_MOCK=1     → モック（AIを呼ばない。デモ当日の保険）
ANTHROPIC_API_KEY  → Anthropic Claude (claude-opus-5)
AZURE_PROXY_KEY    → Azure OpenAI 互換プロキシ (gpt-5.1)  ← 採用
いずれも無し        → モック
```

#### 採用したモデル

学校配布の Azure OpenAI プロキシで使えるモデルを、**実際の成分表示画像と実際のプロンプト**で比較した。

| モデル | 抽出 | 判定 | 備考 |
| :--- | :---: | :---: | :--- |
| gpt-4o-mini | 5.3秒 | 3.1秒 | 「イブプロフェン」を**「いブプロフェン」と誤読**。商品名も「イヴA錠」 |
| gpt-4o | 5.2秒 | 11.9秒 | 正確だが判定が遅い |
| gpt-5-mini | 10.0秒 | 18.5秒 | 成分名に分量が混入（「イブプロフェン 150mg」） |
| **gpt-5.1** | **4.7秒** | **4.1秒** | **最速かつ正確。抽出・判定とも採用** |

**成分名の正確さは照合の前提**である。「いブプロフェン」では在庫の「イブプロフェン」と一致しないため、抽出側も安いモデルに落とせない。**これは速度とコストではなく、機能の成立条件**として扱う。

#### 実装上の差異

| プロバイダ | 抽出 | 判定 | 出力上限 |
| :--- | :--- | :--- | :--- |
| Anthropic | `claude-opus-5` / effort `medium` | `claude-opus-5` / effort `high` | `max_tokens: 16000`（thinking 分を含む） |
| Azure | `gpt-5.1` | `gpt-5.1` | **`max_completion_tokens: 4000`**（gpt-5 系は `max_tokens` を受け付けない） |

**Anthropic 経路で thinking を無効化してはならない** — 無効化するとツール呼び出しや内部タグが本文テキストに混入する既知の失敗モードがある。レイテンシは `effort` で調整する。

**チューニング方針**：NFR-01（10秒）を超える場合、下げるのは**抽出側だけ**。判定は評価対象そのものなので下げない。

#### コスト

**学校配布のプロキシを利用するため、追加の費用は発生しない。**

> **v1.4 で変更**: v1.3 までは Anthropic API を前提に「1スキャン約15円／検証30〜40回で約600円」と試算していた。Azure プロキシの利用により、この費用は不要になった。
> ただしプロキシには**利用枠とレート制限**があり、本選（2026年10月）まで有効である必要がある。Anthropic 経路のコードは残してあるため、必要になれば切り替えられる。

#### 実測レイテンシ

| 環境 | 抽出 | 判定 | 合計 |
| :--- | :---: | :---: | :---: |
| ローカル | 4.7秒 | 4.1秒 | **8.6〜9.3秒** |
| 本番（コールドスタート込み） | | | 10.6秒 |

ローカルでは NFR-01（10秒以内）を満たす。

### 7.6 実装リファレンス（TypeScript）

```ts
// ステップ1：Vision + 構造化出力
import Anthropic from '@anthropic-ai/sdk';
import { z } from 'zod';
import { zodOutputFormat } from '@anthropic-ai/sdk/helpers/zod';

const ExtractionSchema = z.object({
  product_name: z.string().nullable(),
  category: z.enum(['市販薬', 'スキンケア', 'ヘアケア', 'サプリ', '不明']),
  form: z.enum(['錠剤', 'カプセル', '化粧水', '乳液', 'クリーム', '軟膏', 'シャンプー', '不明']),
  ingredients: z.array(z.string()),
  confidence: z.enum(['high', 'medium', 'low']),
});

const client = new Anthropic(); // ANTHROPIC_API_KEY はサーバー環境変数

const res = await client.messages.parse({
  model: 'claude-opus-5',
  max_tokens: 16000,   // thinking トークンもここから消費される。切り詰めない
  output_config: { format: zodOutputFormat(ExtractionSchema), effort: 'medium' },
  // thinking は指定しない（既定の adaptive のまま。§7.5）
  system: EXTRACTION_SYSTEM_PROMPT,
  messages: [{
    role: 'user',
    content: [
      { type: 'image', source: { type: 'base64', media_type: 'image/jpeg', data: base64Image } },
      { type: 'text', text: 'この商品パッケージから成分情報を抽出してください。' },
    ],
  }],
});

// parsed_output は失敗時 null になり得るためガードする
if (!res.parsed_output) throw new ExtractionError();
```

**実装上の注意（SDKの現行仕様）**

- 構造化出力は `output_config.format` を使う。旧 `output_format` パラメータは非推奨
- assistant プレフィル（応答の書き出しを仕込む手法）は現行モデルで **400エラー**になる。使わない
- **`max_tokens` は thinking トークンも消費する。** adaptive thinking が既定でオンのため、4,000程度に絞ると出力が途中で切れて再試行が発生する。非ストリーミングでは 16,000 を既定とする
- `thinking` を明示的に無効化しない（§7.5）
- SDKのHTTPタイムアウトは **ミリ秒**指定（TypeScript SDK）。`timeout: 60_000` のように書く

## 8. API仕様

### 8.1 `POST /api/analyze`

画像1枚を受け取り、抽出と判定をサーバー側で連続実行して返す。**クライアントからのAPI呼び出しはこの1本のみ。**

**Request**

```jsonc
{
  "image": "data:image/jpeg;base64,...",  // 必須・長辺1568px以下・最大5MB
  "stock": [ /* StockItem[] 全件 */ ]      // 必須・localStorage から送る
}
```

**Response 200**

```jsonc
{
  "extraction": { /* ExtractionResult */ },
  "judgement":  { /* Judgement */ },
  "elapsed_ms": 4210
}
```

**Response エラー**

| status | code | 発生条件 | クライアント挙動 |
| :---: | :--- | :--- | :--- |
| 400 | `INVALID_IMAGE` | 画像が無い／サイズ超過／形式不正 | 「画像を選び直してください」＋再選択 |
| 422 | `EXTRACTION_FAILED` | **`ingredients` が空**（成分表示を読み取れなかった） | 「成分表示に寄せて撮り直してください」＋再撮影 |
| 429 | `RATE_LIMITED` | APIレート制限 | 「少し待って再試行」＋リトライボタン |
| 500 | `UPSTREAM_ERROR` | Anthropic API エラー／タイムアウト | 「通信に失敗しました」＋リトライボタン |

**エラーレスポンス形式**

```jsonc
{ "error": { "code": "EXTRACTION_FAILED", "message": "成分表示を読み取れませんでした" } }
```

> **`confidence` は422の条件に含めない。** `confidence: 'low'` でも `ingredients` が1件以上あれば判定は実行し、判定カードに「読み取り精度が低い可能性があります」の注記を添える。低確信を理由に判定を止めると、実機デモで最も起きやすい「少しボケた写真」で必ず失敗する。

### 8.2 処理シーケンス

```
Client                    Route Handler              Anthropic API
  │                             │                          │
  │─ POST /api/analyze ────────>│                          │
  │  {image, stock}             │                          │
  │                             │─ ステップ1（Vision）─────>│
  │                             │<── ExtractionResult ─────│
  │                             │                          │
  │                             │  ingredients が空なら 422 で打ち切り
  │                             │                          │
  │                             │─ ステップ2（判定）───────>│
  │                             │<── Judgement ────────────│
  │                             │                          │
  │                             │  consult_recommended をサーバー側で強制上書き
  │<── 200 {extraction,         │                          │
  │        judgement}           │                          │
```

### 8.3 設計上の決定事項

- **APIは1本に集約する。** 抽出と判定を別エンドポイントに分けると往復が2回になりレイテンシが倍増する。分割の価値（技術力の説明）は§7.2 の設計思想であって、エンドポイント数ではない
- **ストックはリクエストごとにクライアントから送る。** サーバーは状態を持たない（DB不要の根拠）
- **タイムアウトは Route Handler 側で60秒**。Vercel の関数実行上限（現行300秒）には余裕で収まる
- **`stock` はクライアント由来の入力として検証する。** 件数上限（50件）・文字列長上限をサーバー側で課し、そのままプロンプトへ結合しない。デモではシード固定だが、外部入力をLLMに渡す経路であることは仕様として明示しておく

### 9.2 画面①：マイストック

| 要素 | 仕様 |
| :--- | :--- |
| ヘッダー | 「マイストック」＋ 総件数 ＋「編集」ボタン |
| カテゴリ見出し | 処方薬 / 処方薬(外用) / 市販薬・サプリ / スキンケア / ヘアケア / ボディケア の6区分。**タップで開閉する** |

| 処方薬バッジ | `isPrescription: true` に「処方」バッジ。**判定の根拠が可視化される** |
| FAB | 右下固定・「スキャン」・カメラアイコン |

#### 一覧の折りたたみ

在庫は使うほど増える。件数が2桁を超えると縦スクロールが長くなり、目的の項目に届かなくなるため、
**カテゴリ単位で折りたたむ**。

| 仕様 | 決定と理由 |
| :--- | :--- |
| 初期状態 | **すべて展開**。閉じた状態を初期値にすると初回起動で在庫が見えず、「家の棚を基準にする」という前提が伝わらない |
| 開閉状態の保持 | `overlai.collapsed.v1` に保存。スキャン画面から戻っても保たれる（撮影の流れを止めない） |
| 閉じているときの表示 | 中の品名を1行に要約して残す。何が隠れているか分からない状態を作らない |
| 期限アラートを含むカテゴリ | 見出しに琥珀色のドットを出す。**折りたたみで警告を見落とさせない** |

#### 編集・削除

導線は2つある。**主は項目のタップ**で、編集モードは補助として残す。

| 導線 | 仕様 |
| :--- | :--- |
| **項目をタップ**（主） | 下から操作シートが上がる。「編集する」「削除する」を選ぶ |
| 編集モード（補助） | ヘッダーの「編集」で入る。各行に編集・削除のボタンが並ぶ。複数件を続けて消すときはこちらが速い |

**なぜタップを主にするか。** 一覧の項目に触れたら中身をいじれる、というのが先に手が出る動きであり、
「まず編集モードに入る」という前置きは、その手を一度止めてしまう。

| 仕様 | 決定と理由 |
| :--- | :--- |
| タップ領域 | カード全体。編集モード中のボタンだけを前面に置き、両方の導線が競合しないようにする |
| 触れることの示唆 | 各行の右端に `>` を出す |
| 編集 | どちらの導線も `/stock/new?id=` を再利用する。追加画面と同じフォームなので、覚えることが増えない |
| 削除の確認 | **二段階**。localStorage には履歴が無く、誤タップを取り消せないため。シートでは「削除すると元に戻せません。判定の基準からも外れます」と理由も示す |
| シートを閉じる | 背景のタップ・`×`・Escape |
| 初期化 | 編集モード中のみ表示。シードに戻す（開閉状態・服薬記録・プロフィールも消える） |

### 10.1 将来のネイティブ化を見据えた分離方針

**デモはWebアプリで確定**（実装コスト・ストア審査・審査員がその場で試せること、いずれの観点でもWebが妥当）。ただし Phase 2 以降でネイティブアプリ（React Native / Expo）へ移行する可能性があるため、移植コストを抑える分離を**最初から守る**。

| レイヤ | 配置 | ネイティブ移行時の扱い |
| :--- | :--- | :--- |
| 判定ロジック・プロンプト・型定義 | `lib/prompts.ts` `lib/types.ts` | **そのまま再利用できる**（UIに依存しないため） |
| API（Route Handler） | `app/api/analyze/route.ts` | **変更不要**。ネイティブアプリからも同一エンドポイントを叩く |
| 永続化 | `lib/storage.ts` に閉じ込める | **このファイルだけ**を AsyncStorage 等に差し替える |
| 画面・カメラ | `app/` `components/` | 全面的に書き直し（移植不可） |

> **`localStorage` の呼び出しをコンポーネントに直接書かないこと。** この1点を守るかどうかで、将来の移植が「1ファイルの差し替え」で済むか「全面調査」になるかが分かれる。デモの実装コストは変わらないので、今から守る。

なお、本デモの構成では**バックエンド（判定エンジン）がWeb/ネイティブ共通**になる。ネイティブ化しても作り直すのはUI層だけであり、企画の中核である判定ロジックは資産として残る。

## 11. エラー・フォールバック設計

**本番デモで最も事故が起きるのはカメラである。** 以下は保険ではなく必須要件として扱う。

| リスク | 発生確率 | 対策 |
| :--- | :---: | :--- |
| 実機でカメラが起動しない（権限・ブラウザ差異） | 中 | **画像選択モードを常時表示**（FR-04）。撮影済み画像を用意しておく |
| 会場のネットワークが遅い／不安定 | 中 | 検証済みの商品画像を端末に保存しておき、通信不良時は画像選択モードで確実に流す。**生デモはネットワークに依存するため、録画済み動画を第一の提出物とする** |
| APIがエラーを返す | 低 | エラーカード＋リトライ。白画面にしない（NFR-03） |
| 成分表示が読み取れない | 中 | 422を返し「成分表示に寄せてください」と誘導。**デモでは事前検証済みの商品のみ使う** |
| デモ当日にAPI障害 | 低 | **録画済みデモ動画を用意しておく**（生デモに依存しない） |
| APIキーの費用を負担しない判断 | — | **モックモードを実装済み**（下記） |

### 11.1 モックモード（v1.3で追加）

`ANTHROPIC_API_KEY` が未設定のとき、`/api/analyze` は固定応答を返す。**AIは呼ばれていない。**

| 項目 | 挙動 |
| :--- | :--- |
| 判定シナリオ | `?demo=yellow\|red\|blue` で選択。マイストックからスキャン画面へ引き継がれる |
| 応答時間 | 5.2秒の待機（2段階ローディングが映る程度） |
| 識別 | レスポンスに `mocked: true`、サーバーログに警告 |
| 本物への切替 | **キーを設定するだけ。コード変更は不要** |

これにより費用をかけずにデモ動画を撮影できる。ただし**「AIが判定している」とは説明できない**ため、技術力の評価軸では不利になる。提出前に一度は本物で動かすことが望ましい（Issue #13）。

> **最重要：デモ動画は締切直前に一発撮りしない。実装が最低ラインに達した時点で1本撮っておく。** 撮り直しは何度でもできるが、撮っていない状態からの一発撮りは失敗する。

## 12. 安全性・法務設計

### 12.1 設計原則

| 原則 | 実装 |
| :--- | :--- |
| 診断・治療判断を行わない | プロンプトで疾患推定・用法用量指示を禁止 |
| 断定しない | 「〜の可能性があります」で統一 |
| 根拠を必ず示す | `Reason.ingredient` をスキーマ必須フィールド化（§7.4） |
| 専門家導線を常設する | 全判定色で相談ボタンを表示（FR-10） |
| 医療機器該当性 | 記録・情報提示の範囲に留め、診断機能を持たせない |
| 要配慮個人情報の保護 | ストックは端末内保持。サーバーに永続化しない（NFR-06/07） |

### 12.2 免責文言（判定カード下部に固定表示）

> 本アプリは一般的な成分情報を提示するものであり、診断・治療の判断を行うものではありません。実際の使用可否は薬剤師・医師にご相談ください。

### 12.3 審査員の想定質問と回答

| 想定質問 | 回答 |
| :--- | :--- |
| 「AIが間違えたら危険では？」 | 判定理由に必ず成分名を併記し、利用者が根拠を検証できる形にしている。断定表現はプロンプトレベルで禁止し、赤判定では相談導線をサーバー側で強制している |
| 「医療機器に当たらないのか？」 | 診断機能を持たず、記録と情報提示に留める設計。機能追加時に都度ガイドラインを確認する |
| 「服薬情報を扱うリスクは？」 | ストックは端末内保持。サーバーに永続化せず、判定時のみメモリ上で処理する |
| 「全部黄色になるのでは？」 | 🔵判定を実装済み。用途が異なる場合は「買い分けとして妥当」と返す（UC-3） |
